# OmniSearch (`osearch`): the full reference

Every command, engine, fetch tier and setting in detail. The [README](../README.md) is the short version; `osearch config show` prints every setting with its current value, and `osearch ui` shows the same as a web page.

Based on [paperfoot/search-cli](https://github.com/paperfoot/search-cli) (MIT); see `../UPSTREAM.md` and `../NOTICE.md`.

## Commands

| Command | What it does |
|---|---|
| `osearch "query" [any search option]` | Quick research: search (general mode unless `-m`), fetch the top pages, print a summary. Takes the same options as `search`, e.g. `osearch "crawl4ai alternatives" -m code`. Several questions in one run: each quoted argument is one (`osearch "kopia vs restic" "community: borg backup problems"`; a mode name before a colon sets that question's mode, `-m` the rest's). Arguments with no space (`osearch crawl4ai alternatives`) are joined into one question |
| `osearch search -q ... [-m mode] [--width standard\|wide] [-p engines] [--kind semantic\|keywords\|exact] [-c N] [-f week] [-d site] [--region in] [--fetch N] [--snowball N] [--parent RUN] [--platforms tiktok] [--no-cache] [--reddit-login] [--code-search] [--synth\|--no-synth] [--jina-deepsearch\|--no-jina-deepsearch]` | One query with options (`-m shopping --region in` for Indian prices, `-m forums` for forum threads only) |
| `osearch run request.json` | Several different queries, URLs, depth. `osearch help run` prints the format with the defaults from the loaded config (it cannot drift from the code); a misspelt field is ignored and the summary warns about it |
| `osearch fetch <url>... [--via fetcher] [--parent RUN] [--fresh]` | Pages through the tiers (or one named fetcher, `wayback` included), e.g. `osearch fetch https://docs.astral.sh/uv/ https://github.com/astral-sh/uv/issues/1 --parent <run>`. `--fresh`: Firecrawl and Jina read the page anew instead of from their cache |
| `osearch crawl <url> [--topic X] [--max-pages N] [--include g] [--exclude g] [--resume RUN] [--any-path]` | A whole site: llms-full.txt alone when the site has one; else llms.txt's links merged with the sitemap (seed folder and root), else donsetch's map, else the seed's links. `--topic` matches addresses and link text only. Stops at 50 pages by default and prints the `--resume <run>` command that continues it. `--resume` (or `--parent`) with another seed adds that part of the site to the same run; when docs sit in sibling folders the crawl leaves out, the summary names them with the command |
| `osearch research "question" [--engines tavily,youcom,exa,parallel] [--depth light\|standard\|deep] [--approved] [--parent RUN] [--collect RUN] [--wait]` | The engines' own research agents as background tasks. Costly: without `--approved` it only prints the cost estimate. Agents show the user the estimate and ask first |
| `osearch synth [RUN] [--wait] [--all]` | AI synthesis of a run's latest round (default: the last run): a cited answer in `synthesis.rN.md` and `synthesis.md`, every quote checked against the saved pages. `--all` reads every round; `--wait` hands over one still running in the background |
| `osearch wait RUN [--jina-deepsearch]` | Waits for a run's background work (late pages, a background synthesis) and prints what landed. Agents start it as a background command, so its exit is their notice. `--jina-deepsearch` waits for the run's Jina DeepSearch instead (up to `jinadeepsearch.wait`, 6 minutes; the job keeps going after) and prints its answer. `fetch --wait` and `synth --wait` still work |
| `osearch replay [RUN] [--top N]` | Ranks a run's saved results again with the current ranking (Jina's reranker blended in) beside the ranking it had, and lists what would move in and out of the fetched set. No engine calls; about 3k Jina tokens |
| `osearch read p3` / `p3#4` / `p3 --find words` / `p3 --full` | A page of the last run (or `--run RUN`) |
| `osearch grep <regex> [--run RUN]` | Every matching line, labelled page and section |
| `osearch runs [--find topic]` | Past runs; check before new research. `--find` matches whole words in each run's topic, queries and page titles, best first; when nothing matches, a labelled loose pass looks for word fragments in the summaries. Runs not in the index (stopped, killed, or still running in another session) show as `[unfinished]` |

| `osearch login <site>` / `--list` / `--forget site` / `--import-crwl [sites]` / `--import-file cookies.txt [site]` / `--as NAME` | Saved sessions, sent at every tier for allow-listed sites. The window is Edge with its own profile; it saves only when a lasting login cookie appears. `--as alt` keeps a second login of a site beside the main one (its own browser profile); for Reddit see "Reddit accounts" below. `--list` and `doctor` show each login's expiry (doctor warns 14 days ahead). The store is DPAPI-encrypted (this Windows user only) and is never overwritten when it cannot be read |
| `osearch usage` | Every engine's balance in one table: live where the vendor has a balance check, else estimated from the configured allowance |
| `osearch stats` / `doctor [--probe]` / `update [--check]` / `providers` / `config show\|set\|path` / `cache-clear` | Ledger, health, outside tools |

## Engines

exa, tavily, jina, youcom (keyed: environment variables, the file named by `paths.envfile`, or `[keys]` in the config), donsetch (keyless metasearch), reddit + hackernews + devto (community), github + ghissues (through `gh`), youtube (yt-dlp), bluesky (`BSKY_HANDLE` / `BSKY_APP_PASSWORD`), xbird (X with the saved x.com login, off unless `research.xbird`), plus the upstream engines when a key is set (serper, brave, linkup, parallel, perplexity, serpapi, xai). ScrapeCreators platforms, paid in one-time credits: threads, tiktok, instagram join social questions (at most three credits a question, while the balance allows); youtubesc and facebook only when a request names them.

**Mode:** a query without `-m` runs in general mode; the calling agent picks the mode. Only a bare address is decided by osearch (it is fetched). The old keyword rules ("paper" -> academic, "latest" -> news ...) misfired and are off (`router.rs` `WORD_RULES`).

Side searches osearch adds are labelled after their query (`q1r`, `q1f`, `q1g` ...); the extra rounds live in `src/rounds/`.

- **Community mode** (Reddit, Hacker News and dev.to by default) also runs:
  - **Reddit:** Reddit's RSS search (the `reddit` engine; one request a minute per IP without a login, shared by every osearch process, so later questions in the same minute skip it), Brave and You.com (Serper when one can't run) limited to reddit.com (`q1r`; Exa returns nothing for reddit.com), search inside up to `research.redditsubs` (4) subreddits (`q1a1`..): those the request names (`--subreddits GrapheneOS,LineageOS`, `"subreddits"`), the two its threads came from most, then ones a free search ("<question> subreddit" on Jina, else Brave; `q1s` in `raw/`) names, kept when the name shares a word with the question or turns up in two results; with the login it is Reddit's own search there (top of the year), without it each one's top threads of the year kept when on topic; and old Reddit's search with the login (`q1l`; `research.redditlogin` = always by default, auto = when fewer than `research.redditmin` threads turned up, never). `--reddit-login` (`"reddit_login": true`) makes it deeper: the second results page and the year's top threads too. Beside it, Reddit's comment search with the login (`q1e`, `research.redditcomments`, on) finds threads whose answer is in a reply; Reddit applies a period to comment search only when it is sorted by date, so with `-f` it sorts by new. Found threads that came without a date get their creation date from Arctic Shift, 100 a call (`research.redditfill`, on). With `-f` (`"since"`), every Reddit search keeps relevance order within that period (`t=week`...), as last30days does; the web engines scoped to reddit.com (`q1r`) and every forum search (`q1f` with SerpApi's `period_unit`, `q1p`, `q1d`, `q1m`, the direct `q1k` searches) get the same period (the Telegram channel finder and the GitHub list do not). Logged-in Reddit results carry the date from their "submitted N days ago" text. A query with no `since` searches all time. When Reddit refuses its own search (every no-login Reddit route is refused from some addresses; the logged-in search is not), a web search of reddit.com answers in its place and cannot apply the period: the summary says so, and each page shows its own date. The Arctic Shift archive's title search is off (`research.redditarchive`; it times out on its server for rare words in big subreddits). Reddit's own pages without a login are off (`research.redditlive` = false). A no-login route Reddit refuses (HTTP 403) is skipped by every run for `research.redditrefused` hours (6; 0 tries it every run), remembered in `reddit-refused.json` in the cache. A thread counts once whatever address it arrives under. The coverage notes list the subreddits searched and why.
  - **Reddit threads:** Arctic Shift saves a post seconds after it is posted and refreshes the post later, but its comments can take more than a day to arrive. A thread an agent asked for by address is read live (Reddit's JSON of the thread through the login; the archive only when live fails or leaves comments out, since it can take 10 s); a thread a run picked is read from the archive, and live only when that copy is young (under 3 days) or has none of its comments, at most `research.redditlivemax` a run round (default 8). Counted per round in `use.rN.json` in the run folder, so a run's background finisher shares the count. Live thread reads and logged-in Reddit searches are recorded in `calls.jsonl` (`reddit-live`, `reddit-login-search`) with the account in the request field. A thread served by the archive alone carries a stamp: "Reddit archive copy (Arctic Shift) of a post 5 years old; scores as the archive last saved them".
  - **Reddit accounts:** the run's own Reddit use (its logged-in searches, live reads of threads it picked) goes through `research.redditaccount` (`alt`: `osearch login reddit.com --as alt`); pages an agent asks for go through the main login. Logged-in requests are paced at `research.redditpace` a minute (30, a burst of five allowed), shared by every osearch process. Side by side (`research.redditsidebyside`, off), every other logged-in search goes through the main login at once, each account at its own pace; the main login's share counts against `research.redditmainmax`. Faster, but twice the requests from one address. When the run account fails, the main login steps in for at most `research.redditmainmax` (8) calls a round, and the notes say to log the run account in again only when its page shows it logged out; when the main login fails on an asked page, the run account tries.
  - **dev.to:** the question's likely tags (main words joined, then each), most reacted first, on-topic only.
  - **Forums:** Google's forum filter (`q1f`): SerpApi's `google_forums` (monthly allowance), else Serper with `udm=18` (one-time credits), else a forum-word query on Brave; a meaning-based angle on Parallel (`q1p`); GitHub Discussions (`q1d`) and Lemmy (`q1m`); and forums searched directly (`q1k1`..): the forum hosts this run found plus built-in forums whose topic words match the question (two words, one when the question has only one or two), through their own Discourse search (when it fails, `site:` instead), else `site:` on Brave and Jina at once (two at most). All of them run at once. The loose sources (these, Reddit RSS, dev.to, subreddit listings) keep only on-topic results (`src/relevance.rs`, from last30days: generic words like "best" or "review" alone do not count).
  - **Remembered forums:** a seed list of well-known forums by topic (`src/rounds/forums.rs`) plus every forum a community run meets, saved in `forums.json` in the data folder with how often it was seen and whether it runs Discourse (checked once and remembered). Only the built-in forums carry topic words (`load` sets them from the seed list every time): a question's own words are never saved, because they filled every forum's list with ordinary words. A forum outside the seed list is searched directly only when the run's own results include a thread from it.
  - **Telegram** (also in social mode): `site:t.me` on Brave and Jina (`q1n`) finds public channels; the two most found are searched inside for the question's words (`q1n1`, `q1n2`, `t.me/s/<channel>?q=`).
  - **Coverage** gains run-wide lines: the subreddits searched and why, and Reddit threads by route, forum and discussion threads, Hacker News, Telegram.
- **Social mode:** YouTube (yt-dlp), X (`xbird`, when on: X's top posts through the saved login, on-topic only; `-f` adds X's `since:` date), Bluesky (when keyed), Telegram, and Threads, TikTok, Instagram through ScrapeCreators (one credit each). No word in the query picks a platform: `--platforms xbird,bluesky` (`"platforms"`) runs exactly those.
- **GitHub beside web questions:** general, community and deep questions also search GitHub (`q1g`; `research.githubbeside` = all, general for general and deep only, or off); only repos with most of the question's words in their name or description are kept (`research.githubminstars`, 0 by default, sets a star floor; stars order the list). They are listed apart in the summary ("GitHub projects": stars, last push, archived) and give at most two fetched pages.
- **Code mode** also searches the top repo's topics by stars (`q1t1`..), projects updated in the last four months (`q1n`), and the repos listed in the matching awesome lists (`q1w`). **Code search** (repos whose files use something) runs for "examples of X", "projects using X", "who uses X" questions, or with `--code-search`.
- **Alternatives questions** ("alternatives to X", "X alternatives", "tools like X", "similar to X"): osearch finds X's own page (its GitHub repo, else a site named X, else one `gh` search). For a repo it adds GitHub repos sharing its topics by stars (`q1xt1`..), or described like it when it has no topics (`q1xd`); for a site, Exa's pages-like-it search (`q1xs`, which mostly returns pages about the product itself) and Exa searched with what the site says about itself (`q1xd`, the site's own words without its name; a table-like snippet is skipped for the page title). On a repo `q1xs` is not used. The `x` keeps these labels apart from the code and community rounds' own. When X's page can't be identified it says so and adds nothing.
- **GitHub searches** send each word as its own argument (`gh` searches one quoted argument as an exact phrase), and drop a bare year (it matched issue and PR numbers), using it as an updated-since date instead.

## Engine widths and balances

- **Width** (general mode, `--width` or `"width"` in a request, default `research.width` = wide for now): **wide** runs every web engine with balance to spare; **standard** runs about six, from `research.standard` in order (default: donsetch, exa, youcom, parallel, brave, tavily, with jina and linkup standing in). **Deep** mode stays separate: every engine plus GitHub, Jina and X, on heavier settings, more pages (`research.deepfetch`), and Jina DeepSearch beside it (below). Engines named in a query always run as named.
- **Balance-aware picking**, in this order: free engines always; monthly refills, expiring credits (Parallel) and plentiful balances (You.com, Jina) by default, monthly ones paced (held back when more than 15 points ahead of the month); finite caps (Serper, ScrapeCreators) only when standard has fewer than four engines, and in wide or deep only above 20% left; anything stops at 5% left. Held-back engines are listed in the summary.
- **Balances**: `[balance.<service>]` in config: `kind` (monthly, onetime, expiring), `amount`, `unit`, `unitprice` (USD per unit), `resetday`, `expires`, `checked`, `plentiful`. `osearch config set balance.exa.amount 30` (dates it today). Live checks: Tavily, Firecrawl, Linkup, SerpApi, You.com, Jina (dashboard endpoint), Serper (`/account`), Brave (costs one request, so only `osearch usage`). Exa, Parallel and ScrapeCreators are counted from the ledger. A run refreshes live readings older than 12 hours first.
- **Results per engine** (no `-c`): 20 where the price does not change (Tavily, Brave, You.com, Linkup, Jina, Parallel, SerpApi) and for Exa ($1/1k per result past 10: $0.017 a query), 10 for Serper (a Google page), 12 for donsetch.
- **Reranker** (`research.rerank`, off): Jina's reranker scores the top 100 results (title and snippet) against the run's question, and that score is blended half and half with osearch's own before pages are picked. Judge it on past runs with `osearch replay` first.
- Brave's free plan takes one request a second, so its requests go one at a time, across osearch processes too (the next free moment is kept in `brave-turn.txt` in the cache).

## Fetching in a run

- **Which pages:** the request's URLs, then the best result of each query and of each side search of the same kind (community, code), then a second for each question, then two links only one engine found, then the rest by overall rank. Side searches of another kind (the GitHub list beside a web question, alternatives) share at most a third of the pages, the GitHub list at most two. How many (settings, not numbers here: `osearch config show`): `research.quickfetch` for a quick search, `research.fetch` for request files, `research.communityfetch` when every query is in community mode, `research.deepfetch` when every query is deep. A request's own questions past the third each add `research.fetchgrow` pages, up to `research.fetchmax` (side searches do not count). `--fetch N` or `"fetch": N` asks for a number: below the run's default it is raised to the default (`research.fetchfloor`; `0` stays search-only), above it it is used as given. The summary says how many pages were read of how many results, and when a request overrode a default. 10 fetched at once (`research.concurrency`). Page numbers are given when the list is picked, so `p1` is the first pick.
- **While Reddit searches:** on a community run the logged-in Reddit searches (paced) usually finish last, so the pages from everything else start fetching while they run, with room kept for one page per Reddit side search; once they are in, the rest of the pages are picked from all results.
- **Fetches into a run** (`osearch fetch <url> --parent RUN`) join its latest round: the pages are added to that round's list (`picks.rN.json`), the round's summary stays, and `fetches.jsonl` records each fetch. Only searches open a new round.
- **Saved as they finish:** the run folder, request and an "unfinished" summary are written first; each engine answer as it arrives; each page the moment its fetch ends; `results.jsonl` before any fetch. A killed run keeps all of that and shows in `osearch runs` as `[unfinished]`.
- **Summary:** the header says how many pages were read of how many results (and the run's default); "This request differs from the defaults" lists what the request set (a `fetch` below the default, a `cost_cap`, a `width`); "Queries" has one line per search (its mode, text, links found, new ones, per-engine counts, "narrowed by kind" when a `kind` cut the engines); "Top results" shows the first `research.topresults` results with the date the engine gave and the snippet of the first `research.snippetprefer` engine that found it (clipped to `research.snippetchars`; else the longest); every engine's snippet is in `results.jsonl`. Each one ends with a token line (this summary, pages fetched, results index, raw answers) and `Next:` commands that name the run (`--run <id>`), so a second session's newer run is never read by mistake.
- **Returning early:** three spare pages start beside the picked ones. The fetch step ends once as many good pages are in as were picked, or after 10 s in a quick search and 20 s otherwise (`research.quicksoft`, `research.softtime`), whichever comes first; 30 s / 90 s (`research.quicktime`, `research.fetchtime`, `--fetch-time`) stay the outer limit. Pages asked for by address are waited for up to the outer limit (one still fetching then finishes in the background like any other) and do not count toward "as many as were picked".
- **Background pages:** pages still fetching then are stopped and handed to a separate `osearch fetch --finish <run>@<round>` process, which continues each from the next fetcher it had not tried and saves it under its number; a page that is still not done at its five-minute limit is saved as not fetched (`too_slow`) with the retry command. Each round has its own marker files (`pending.rN.json`, `fetch.rN.running`), so a follow-up round never disturbs another round's pages. Pages that finished while the step was stopping are kept, and the background never skips a fetcher that worked. The summary lists them and tells the agent to start `osearch wait <id>` as a background command (it waits up to about five minutes and lists what came in). A background synthesis waits for them first (up to 2 min); a synthesis in wait mode reads the pages that are in and says how many were still fetching. Crawls wait for every page, except those of a site that keeps walling us.

## Fetch tiers

0. The site's own data door: Reddit threads (live or archive, see "Reddit threads" above), HN threads, Discourse threads (every post, from `/t/<id>.json`), GitHub (`gh`), StackExchange API, npm / PyPI / crates.io, arXiv (HTML paper, else abstract), YouTube (yt-dlp metadata and captions), Bluesky threads (public API: the post, the posts above it, every reply), Telegram channels (`t.me/s/<channel>`: recent posts, no login; groups and private channels have no preview).
1. donsetch (Chrome fingerprint, challenge solving, honest labels); on forum-thread addresses (`research.forumboth`, on by default) donsetch and the built-in direct/stealth fetchers run together and the copy with more words is kept, since each loses replies on some forum software; the built-in direct and stealth fetchers as the safety net (first, with saved cookies; Reddit threads go to donsetch first).
2. The light browser (`tools.lightbrowser`: moli by default, obscura, or off) and headless Chromium (Playwright's) over CDP, raced, with the Jina reader racing them too (when keyed and paid readers are allowed): the first good page wins and the others are stopped; three Chromium windows at most. Only for JavaScript-built pages. Chromium scrolls to the end until the page stops growing (content loaded on scroll); moli does not scroll. moli takes the site's saved login as a cookie file that lives only for the fetch; its HTML goes through osearch's own converter (moli's markdown loses code blocks and keeps menus). Obscura, when chosen, skips logged-in sites.
3. crawl4ai (`crwl -p main`, scrolled to the end with `scan_full_page`), raced with the Jina reader when Jina did not already run at tier 2, then Firecrawl.
4. The Wayback Machine (`fetch/wayback.rs`): when the page is gone (404/410, no such host), behind a paywall, or every fetcher failed, its newest saved copy (`archive.org/wayback/available`, then the raw `id_` snapshot), stamped with its date; otherwise an honest "bot wall". For a site the site memory says walls every fetcher, the lookup runs beside the other tiers. Never used in place of a page that loaded; crawls skip it; `--via wayback` asks for it.

**Stamps:** every page has a `> Source:` line under its title saying where the copy came from: `read live <time>`, or a Reddit archive copy, Firecrawl's cached copy (Firecrawl serves copies under 2 days old unless asked fresh), a Wayback copy, or a Jina reader copy ("its cache may have served it; age unknown": Jina keeps a cache, so it is never labelled live unless `--fresh`). The line also carries the page's own date when known (` · page dated 2026-07-04`: the article metadata, else the first date the markup carries, else the date the engine gave the result). A fetcher's notes (a Reddit thread's missing comments, a login that stepped in) are a separate `> Note:` line. The summary line of a page shows its stamp only when it was not read live, plus the note and the date. Fresh reads (`--fresh`, `"fresh"`, and any run with `-f`/`since`) send Firecrawl `maxAge: 0` and Jina `X-No-Cache`.

**Repeats:** each page's overlap with the run's earlier pages is recorded (`same_as`, `overlap` percent in `pages/index.jsonl`, and "N% same as pX" in the summary). `research.dedupe` (off) leaves pages at least `research.dedupemin` (80) percent the same out of synthesis.

Waits per fetcher (from 459 measured pages, about three times the slowest success): donsetch 12 s, direct and stealth 10 s, moli and Obscura 15 s, Chromium 25 s, crawl4ai 30 s, Jina 12 s, Firecrawl 20 s.

**Site memory** (`sites.json` in the data folder, never expired): every fetcher's tries, successes and failure kinds per site, with recent outcomes. A fetcher that failed a site at least three times on two days or more, while another worked there, starts after the others for that site; it is still tried if they all fail. A site whose pages failed at every fetcher the same way sends its pages straight to the background. `osearch stats` shows each fetcher's success times (p50, p90, slowest), failures by kind, the pages finished in the background, and the sites no fetcher gets past, paid readers included: the evidence for tuning the waits above.

Every result is checked (length, challenge text, sign-in pages, XenForo's error page, the tool's own labels) and stripped of inline base64 pictures. osearch's own converter keeps the whole page instead of the article cut when the cut drops the numbers the page shows, or, on a discussion page (repeated comment or post blocks), when it keeps under 35% of the visible text: article extraction keeps the first post and drops the replies. Stopped fetches leave nothing behind: moli's cookie file is removed even when its fetch is stopped, and each run clears `browser-tmp` entries older than ten minutes. In `raw/`, yt-dlp's answer keeps only the caption tracks osearch reads (its machine-translated caption list was 96% of the file). A sign-in page is a redirect to a login address (last segment `login`/`signin`/`sso`/`auth`..., or a login segment with a return-to parameter) or a short page with sign-in wording; a page merely about logins is content. A domain that does not exist stops at once (`no_such_host`); Chromium's own error page never counts as a page. Outside tools are never pinned: a changed output shape or exit code is a loud CONTRACT WARNING in the summary and the page falls through.

## AI synthesis

A large-context model reads a round of a run and writes a cited answer: `synthesis.rN.md` in the run (the latest is also `synthesis.md`). Its status and short answer are printed under the summary's counts, the full text at the end. A follow-up round's synthesis reads that round's pages and its own question; the earlier rounds come in as the short answers of their own syntheses, never their pages again, so each round is answered by its own synthesis and nothing is overwritten. `osearch synth <run> --all` reads every round instead (`synthesis.all.md`). It is off until an endpoint and model are set: `synth.url`, `synth.model`, `synth.api` (`anthropic` for `/v1/messages`, `openai` for `/v1/chat/completions`: OpenAI, OpenRouter, Ollama, LM Studio and most local servers), `synth.key`, `synth.effort`. A cheap model with a large context window is the right fit: it reads 50-300k tokens per run.

- **When:** `synth.enabled` auto, on or off; auto runs it for request files (`synth.requests`) and deep mode (`synth.deep`), not quick searches (`synth.quick`), never for plain `fetch`. `--synth` / `--no-synth` (`"synth": true|false`) decide one run.
- **Wait or not:** `synth.wait` = wait (summary and synthesis together) or background (the summary at once; a separate `osearch synth <run>` writes it, `osearch wait <run>` prints it). A run with no pages (`--fetch 0`) has none.
- **What it reads** (settings): every fetched page with `[p3#4]` marks at its sections (`synth.pages` = full or sections), up to `synth.pagecap` (30k) tokens a page: a longer page goes as its opening plus its best sections for the question, in page order; the engines' own answers marked unverified (`synth.answers`, from the round's summary); every engine's snippet of each of the round's results that has no fetched page, pages that failed to fetch included, the engines of `research.snippetprefer` first (`synth.snippets`, at most 80 results). Up to `synth.maxinput` (300k) tokens in all: over that, the top pages whole and the rest as their best sections (4k each), so every page is represented; best pages first; one text block per page (some endpoints refuse a block over 1 MiB).
- **The connection:** its own HTTP client (no idle cut: a non-streaming answer is silent until done), `synth.timeout` seconds. One `x-session-id` per synthesis; a dropped connection is re-sent at once with the same id and body (a proxy that keeps sessions can treat it as a retry of the same turn). A failure, a crash included, is one line with the command to run it again; the run itself is never affected.
- **The prompt** is built in (`prompts/synth.md`, based on LangChain Open Deep Research's report prompt); `synth.prompt` names a file read at every run instead, for tuning without a rebuild. If the answer has `<short>` and `<full>` parts (`synth.shorttag`, `synth.fulltag`), `synth.show` picks what the agent sees: full, short or both.
- **What is kept:** beside each synthesis, the request exactly as sent (`synthesis.rN.request.json`; the key travels in a header and is never in it), the endpoint's raw answer (`.response.json`) and its figures (`.json`: question, model, tokens, cost, time, quotes, and how each page was sent: whole, as an excerpt, or left out). A second synthesis of a run while one is under way is refused.
- **Quote check:** every quoted phrase of 20 characters or more is compared with the page it cites (case, spacing, quote marks, dashes and markdown links evened out, otherwise exact) and marked `[verified]` or `[not found in p3]`; citations to sections that don't exist are marked too; the "Gaps" part is not checked. The header counts them.
- **Cost:** the endpoint's own figure when it reports one (`usage.cost_usd` with `usage.cost_known`); else tokens priced from `synth.inprice` / `synth.outprice` (USD per million tokens), or from a price list file in OpenRouter's catalogue shape (`synth.prices`), shown as "estimated". "price unknown" when nothing has the model.

## Jina DeepSearch

Jina's own research agent (`jina-deepsearch-v1`) searches, reads and reasons on its own. It starts at the beginning of every deep run (`jinadeepsearch.modes` = deep; `research` adds `osearch research`; never quick searches) in a separate process that nothing waits for, on the run's first deep query, or `"jina_deepsearch": "<question>"` in a request (`true`/`false`, `--jina-deepsearch`/`--no-jina-deepsearch` per run). One runs at a time per run folder: a deep follow-up round starts its own only once the earlier one has landed. Its answer lands as the run's next page ("Jina DeepSearch answer", with the quotes it cites and the pages it read), and every page it visited joins `results.jsonl` (engine `jina-deepsearch`). The summary tells the agent to start `osearch wait <id> --jina-deepsearch` as a background command; that waits up to `jinadeepsearch.wait` (360 s) and prints the answer, while the job keeps going until it lands or `jinadeepsearch.stop` (1,200 s, a hung connection). Settings: `jinadeepsearch.budget` (500,000 tokens), `jinadeepsearch.effort` (low, medium, high). Measured 2026-11-09 at medium: 219 s, 447k tokens (0.05% of the Jina balance), 62 pages visited, 5 read.

## Research mode

`osearch research` runs Tavily Research (model mini, or pro at `deep`), You.com Research (effort lite / standard / deep), Exa's agent (effort low / medium / high, with a hard budget of $0.10 / $0.30 / $1.00) and Parallel's Task API (processor core / pro / ultra, text report) as background tasks. Prices (vendor pages, 2026-11-08): Tavily 4-110 credits for mini, 15-250 for pro, at $0.008 a credit after the free monthly credits; You.com $0.012 / $0.05 / $0.10 a task; Exa $0.012 up to the budget; Parallel $0.025 / $0.10 / $0.30 a completed run. Task ids go to `research-tasks.json` in the run; `--collect` (or `--wait`) saves each finished report as a page with its sources. The ledger gets the real cost: Tavily's reported credits, Exa's measured cost, You.com's fixed price.

## Where things are

- Config and data: the platform's own folders by default (`osearch config path` prints the config file). One folder for both instead: `OMNISEARCH_HOME`, or a file named `omnisearch-home` next to the executable whose first line is the folder. Inside it, `config/config.toml` and `data/`: `logs/` (cost ledger), `cache/`, `cookies.json` (saved logins), `forums.json`, `tools/` (donsetch, moli, Obscura), `ui/` (the web UI's request files and insights cache), `login-profile-edge/` (plus `-<account>` profiles).
- Runs: `<archive>/runs/<id>/` (request.rN.json, calls.jsonl, raw/, results.jsonl, picks.rN.json, pages/, summary.md, synthesis.rN.md with its request, response and figures, synthesis.md, research-tasks.json); index `<archive>/runs.jsonl`. `paths.archive` sets the archive (default: `archive/` in the data folder).
- The built-in synthesis prompt: `prompts/synth.md`.

## Web UI

`osearch ui` starts a local web page (127.0.0.1 only, `ui.port`, 7820 by default): run searches and follow their progress, browse every past run (its searches, results, pages with why each was picked and how it was fetched, a timeline of every call, the summary and synthesis), see each flow of osearch as a map with the settings that steer each step, change settings, and compare engines across runs. The page is built from `ui/` (React, TypeScript, Vite) and packed into the executable; build osearch with `--no-default-features --features stealth` to leave it out. Searches started there run osearch itself with a request file, the same path as the CLI. The API refuses other hosts, and anything that changes something must come from the page itself. `ui.notes` can name a notes server for a review-notes widget (off by default).

## Build

`bash build.sh`: builds the web UI (`npm` in `ui/`), then the release binary, and copies it to `OSEARCH_INSTALL_DIR` when set (a `build.local.sh` beside it can set it; that file is not published). Needs Rust, CMake, LLVM (libclang), NASM on Windows (`OSEARCH_NASM_DIR` when it is not on PATH), and Node.js for the UI. Tests: `cargo test --bin osearch` with the same environment. Release builds for every platform: `.github/workflows/release.yml`.
